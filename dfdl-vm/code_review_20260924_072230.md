## Summary of Changes

### 1. `src/ir/builder/props.rs` — Fixed Property Inheritance Inversion in `merge_ir_props`
- **Issue**: `out.byte_order` and `out.bit_order` were unconditionally assigned from `overlay` before checking `if overlay.byte_order_defined` / `if overlay.bit_order_defined`.
- **Root Cause**: When merging element IR properties (`base`) with container sequence overlay properties (which lacked explicit bit/byte order definitions and defaulted to `MSBFirst`/`BigEndian`), `base.bit_order` (such as `LeastSignificantBitFirst`) was overwritten by `overlay.bit_order` (`MSBFirst`).
- **Fix**: Wrapped assignment of `out.byte_order` and `out.bit_order` inside `if overlay.byte_order_defined` and `if overlay.bit_order_defined` conditional blocks.

### 2. `src/tdml/parser/document.rs` — Corrected Default `part_bit_order_regions` Population
- **Issue**: Standard TDML documents lacking explicit `@bitOrder` attributes had `part_bit_order_regions` populated with implicit `(MostSignificantBitFirst, len)` tuples.
- **Root Cause**: The presence of `part_bit_order_regions` signaled to the VM bit cursor that explicit transmission bit-order regions were present, causing the cursor to override element-level schema `dfdl:bitOrder` declarations with the document-level default.
- **Fix**: Restricted `part_bit_order_regions` output so it is only populated when explicit `@bitOrder` attributes are declared on `<tdml:document>` or `<documentPart>`.

### 3. `src/vm/runtime/cursor.rs` — Streamlined `BitCursor::effective_field_bit_order`
- **Issue**: `effective_field_bit_order` unconditionally checked `if self.transmission_bit_order != BitOrder::MostSignificantBitFirst` and returned `self.transmission_bit_order`, overriding element schema `dfdl:bitOrder`.
- **Fix**: Simplified `effective_field_bit_order` to check `if self.tdml_bit_order_regions.is_some()`, returning region-based transmission bit order when explicit TDML regions are active, and defaulting directly to the element's `schema_order` otherwise.
